# @obsidion/passkey-web

The browser passkey policy for the web fronts: which device may answer a ceremony, which PRF slot becomes the master key, the backup and provider gates, the typed refusals and their copy, and the WebAuthn ceremony wrapper that produces the evidence those rules read. The web wallet and the launch campaign both compose it. A front that composes it carries no rule of its own, so fronts cannot drift from one another.

## Why it sits beside the layering chain, not in it

The chain is `core → contracts → sdk → front-core → web-wallet`. This package sits directly on `core` (the salt, the provider ids, the field modulus, the `PrfSlot` type) plus `@noble/curves` for P-256 public-key recovery, and nothing in the chain imports it. The campaign cannot take `sdk`: sdk compiles the contract artifacts into whatever builds it. `front-core` sits on sdk. So the shared rules live in a leaf that carries no Aztec, no React, no `viem`, and no `Buffer`; SHA-256 comes from WebCrypto.

**May import it:** the web wallet, the launch campaign, and any later web front. **Must not import it:** `sdk` and `front-core`. sdk keeps its own `Fr`-typed derivation; the shared fixture in `test/fixtures/mskPrfParity.json` pins the two derivations to the same vectors.

## Layers

| Folder | What it holds |
| --- | --- |
| `src/policy/` | No DOM. Device posture, the user-agent parser, the phone-reach probe, the provider allowlist and its display names, the refusal errors, the refusal / phone-steps / iOS-floor copy, the environment record, the slot and route rules, the authenticator-class rule, the evidence gates, the backup passkey rules, the ceremony drivers, the creation-provenance rule, and the Aztec-free MSK derivation. |
| `src/ceremony/` | The DOM. `BrowserPasskeyCeremony` over `navigator.credentials` (both salts, attachment and hints, the tab slot), the page-start lock on the browser's own passkey functions (`nativeLockScript`, an inline script a front puts at the top of `<head>`; `nativeLockFor` reads what it did and `keptPasskeyApiFor` the extension wrapper it kept aside), the user handle (the account name and where the passkey was made, `userHandle.ts`), authenticator-data parsing, public-key recovery, byte helpers. Nothing runs at module load, so the root export is safe to import from a node process. |

A change under `src/policy/` that relaxes a refusal, a gate or the provider allowlist reaches every front that composes it, the funded wallet among them. Judge such a change against every consumer's risk, not only for parity.

These rules are worth knowing before reading the code.

**Only measured providers may create a wallet.** The check runs on the id the provider reports, per authenticator class, so a manager id on a hardware key and a key's id on a phone passkey are both refused. An absent or all-zero id passes, because iCloud reports zeros on iOS and Chromium zeros every roaming key's — so on a browser that withholds the id this is steering, not a gate, and the backup, PRF and route gates are what defend the account. `extraProviders` on the creation driver admits ids beyond that set for a consumer's browser tests, whose virtual authenticator reports a fixed id; production passes none.

**The backup gate applies to phone passkeys only.** At creation the response's transports tell a security key, which holds the only copy of its credential by design, from a phone answering over QR; an empty list beside an id attested as all zeros is also a key (the shape Chrome reported for a Trezor under `none` attestation: a compatibility heuristic bounded by the browsers measured), and anything the browser describes less certainly counts as a phone and meets the gate. An assertion carries no transports, so at sign-in the gate exempts any answer from another device and the consumer's anchors decide what it opens. That answer shape still says "key": `impliedKeyTransports` names USB, NFC and smart card (never `ble`, which Chrome reads as the phone route) for another device's answer that cannot be backed up, so a consumer can remember where a key lives on a browser that never created it and send those transports with later requests (`isPhysicalOnly` tells a recorded key list from a synced passkey's).

**A laptop Safari from 18.6 up to 26 mislabels a cross-device answer as its own.** The drivers correct the label under narrow conditions when a consumer says the browser is inside that window; "Route rules" in `docs/account/secret-key.md` states them and what the correction never touches.

**A laptop refuses its own passkey by default; a sign-in may opt in, and a creation only per manager.** The route rule sends a laptop to another device — a phone over QR or a security key — and refuses a `platform` answer, because an unmeasured local route could bind a value no other device reproduces. `runPasskeyAssertion`'s `localAllowed` lets a consumer admit the device's own answer at sign-in: the sheet opens on this computer, no transport restriction is sent (a record naming only `hybrid` must not hide the local copy), and a `platform` answer passes the route check. Its anchors then decide whether that answer opens the account, exactly as for a cross-device one. Creation takes a narrower opt-in: `laptopCreationFor` decides from the browser's Client Hints, or for Safari and Firefox from the user-agent string, which managers this laptop's row admits (`LaptopCreation`), and a consumer passes those as `runPasskeyCreation`'s `localCreation`. The request then asks for `platform`; by default it names `client-device` and `security-key` (`LAPTOP_LOCAL_CREATION_HINTS`), so 1Password's extension stands aside for the browser's own managers, and a consumer that wants the extension passes `client-device` alone (`LAPTOP_LOCAL_HINTS`). The answer is admitted only when it is `platform` (or a key) and its provider id names an admitted manager, and the chained assertion must answer with the credential just created. "Laptop creation" in `docs/account/secret-key.md` states the rows and the refusals.

**A backup passkey keeps only the rules its envelope needs.** A backup passkey's PRF opens an envelope holding the master key, so it only has to give the same PRF back to the same manager later. The backup-flag, route and slot rules above do not apply: a device-bound or laptop-local backup is fine. `runBackupPasskeyCreation` asks for no attachment and names the routes the consumer's pick chose (`BackupAddChoice`, listed by `backupAddOptionsFor` from what the page detected): this device and a security key by default, a password manager's extension, the phone over QR, or a key alone; on a laptop its follow-up read names the same hints, or a key's `security-key` and transports. It admits the first passkey's managers and any security key whose id names no manager, and needs a PRF on this device from a response whose user-verified flag is set, since `hmac-secret` gives an unverified read a different secret. Windows Hello, Proton Pass and Samsung Pass are candidates in `BACKUP_CANDIDATES`: each passes only from this device's own manager, on the OS families its measurement covers, once its `measured` flag is set. Proton Pass is measured on macOS and Android and admitted everywhere but iOS, where its app returns no PRF, Samsung Pass is measured and admitted on Android, and Windows Hello is measured and admitted on Windows. `windowsHelloBackupWarning` gives an add screen the line it shows before the passkey window opens where Client Hints say Windows 10, whose Windows Hello returns no PRF, while Windows Hello is a measured candidate. Every refusal is a `BackupPasskeyRefusedError` with a `kind`. "Backup passkeys" in `docs/account/secret-key.md` has the detail.

**The page-start lock keeps Proton Pass's wrapper aside, and the ceremony routes to it.** On Chromium the lock (`nativeLockScript`) restores the browser's own `create` and `get` over the wrappers Proton Pass's extension assigns before any page script, and keeps a wrapper whose source carries Proton's message name (`PASSKEY_CREATE`, `PASSKEY_GET`) in a frozen slot on `globalThis` (`keptPasskeyApiFor`). `BrowserPasskeyCeremony` calls the kept `get` for any assertion that names `client-device` or sends no hints, and the kept `create` only for a request with `extensionAllowed`, which `runBackupPasskeyCreation` sets on the Proton Pass pick and `runPasskeyCreation` never does; a kept call carries `requestTimeoutMs`, since the extension's bridge can hold a request without end. Proton falls through to the browser's own method when it cannot answer; a front offers it only while the wrapper is kept. The telemetry readers (`passkeyExtensionFor`, `extensionAnswersPasskeys`, `nativeLockFor`) keep reading the restored natives.

## Commands

```shell
pnpm build            # builds @obsidion/core first, then tsc -b
pnpm test             # vitest; test/isolation.test.ts reads dist/, so build first
pnpm typecheck:test   # typecheck the suite
```

The consumers' own scripts build this package before they typecheck, test or bundle.

`test/support/fakePasskeyCeremony.ts` is the one fake authenticator both web fronts' suites drive (real P-256 signatures, a manager × route PRF table). It is test support, not part of the package's exports: a consumer's test support imports it by relative path, the way `packages/web-wallet/test/support/fakePasskeyCeremony.ts` does.
